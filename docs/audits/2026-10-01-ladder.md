# Audit of the information ladder — `docs/_audit_ladder.md`

Read-only audit. No repo files were modified, no model was run, no OpenRouter credits were
spent. Every number below comes from local Python over `data/`, calling the real builders in
`smol_ladder/ladder.py`, re-reading `data/runs/*/<task>/<rung>/result.json`, and parsing
`logs/*.log`. Scripts live in `/tmp` and are not part of the repo.

The two worries put to this audit were (a) the ladder is not well defined, and (b) the tasks
are too easy for it to measure anything. Both are correct, and there is a third problem that
is larger than either: **the headline result in `LADDER.md` does not describe the runs on
disk.** That is Section 0 and it changes how everything else should be read.

> **Note on concurrent changes.** While this audit was running, another process committed
> `31d3e74` ("Make the summary a partition instead of a histogram that double-counts"), which
> fixes the `summarize.py` defect reported in Section 0, and wrote its own
> `docs/_audit_numbers.md`. That process made the repo edits; this audit did not. Where the
> two overlap they agree on the substance: the `test` table in `LADDER.md` is withdrawn and
> the control rescues 23/63 = 36.5%, not 92%. This report is scoped to the ladder *definition*
> and the *task population*, which that audit does not cover.

## 0. The published result and the runs on disk disagree

`LADDER.md` opens with:

> **The failures on this benchmark are overwhelmingly an exploration problem, not a missing-
> information problem.** Of the tasks that failed L1, 165/179 = 92% passed once we handed the
> model a schema dump...

| claim in `LADDER.md` | what is on disk | what is in the logs |
|---|---|---|
| L1 = 184/250 = 73.6% | 187/250 = 74.8% | 4 L1 runs: 71.5%, 72.8%, 74.5%, 74.8% |
| L1+schema = 165/179 = 92.2% | **23/63 = 36.5%** | 23/63 = 36.5% (`rerun_test.log`) |
| L2 = 9/14 = 64.3% | — | 167/181 = 92.3% (`climb_test.log`) |
| L3 = 2/5 = 40.0% | — | 8/14 = 57.1% (`climb_test.log`) |
| L4 = 3/3 = 100% | 6/6 = 100% | 6/6 = 100% (`climb_test.log`) |

Three separate problems, each verified:

**The 92% control figure is not a rescue rate, and the run it came from is not on disk.**
`165/179` traces to `logs/run_ladder_climb.log` (mtime 2026-09-28 20:37). That file contains
**42 real control runs, and 39 of those 42 tasks passed L1** — they were never failures to
rescue. Joining that log against the final on-disk L1 results:

```
Of the 42 controlled tasks: 39 actually PASSED L1, 3 actually FAILED L1
control "rescue" rate among real L1 failures:  2/3  = 66.7%
control pass rate among tasks that already passed L1: 39/39
```

So `41/42 = 97.6%` (the log's own pass rate) and `165/179 = 92.2%` are pass rates over a
population that was mostly already passing. The denominator 179 matches the number of tasks
with a verified reference (181), not the number of L1 failures (63). This run also predates
commit `09365ea` ("Fix a verifier mount that silently graded trials 0.0", 2026-09-29 02:28),
so its grading path contained a known mount-ordering bug.

**The measured control result is 36.5%, and it points the other way.** The current, correct
run — `rerun_test.log`, after the verifier fix — ran the control on all 63 L1 failures and
rescued **23**, or **36.5%**:

```
L1 failures: 63; of those with a control result: 63; control rescues: 23/63 = 36.5%
```

`run_syn_control.log` and `climb_syn.log` also ran the control over the **entire** synthetic
split (275 tasks, including the 179 that passed L1), which is why their headline 75.6% and
71.6% likewise are not rescue rates. The clean synthetic rescue number is **23/96 = 24.0%**.

The claim in `LADDER.md` that "a gain here is a processing gain, not evidence that the task
was underdetermined" survives, but the magnitude it rests on does not. A 36.5% rescue rate
still means most failures are *not* fixed by cheaper reading, which is the opposite of the
headline sentence.

**`summarize.py` double-counted, so the old summary JSON was not a partition. (Fixed
concurrently during this audit, commit `31d3e74`; recorded here because the numbers this audit
quotes predate the fix.)** The old `rung_counts` for test was `L1 187, L1+schema 16, L2 17,
L3 3, L4 3, never 0, no reference 40`, which sums to **266 for a 250-task split** (synthetic:
298 for 275). The cause was in `smol_ladder/summarize.py:76-80`: a task rescued by the
control was recorded in *both* the `L1+schema` bucket and the `L2/L3/L4/never` bucket,
because the control branch had no `continue`. `summary_test.json` now reads
`first_passing_rung = {L1 187, L2 17, L3 3, L4 3, never 0, not climbable 40}` = 250, with
the control reported in its own block. Recomputed with one task in exactly one bucket:

```
L1 failures with a reference : 23      (40 failures have no reference at all)
  rescued by control (not an information result)
  rescued by L2   : 17   (11 of them also passed the control)
  rescued by L3   :  3   (2  of them also passed the control)
  rescued by L4   :  3   (3  of them also passed the control)
```

Note that 20 of the 23 information-rung rescues are also control rescues, so on this split a
hint rung and a no-information prompt are nearly interchangeable — which is the honest
version of the ladder's negative result.

**A real, previously unreported monotonicity violation exists.** `climb_test.log` ran L2 over
all 181 referenced tasks, not only the L1 failures, so the joint L1/L2 table is observable:

```
(L1 pass, L2 pass) -> n
  (True,  True)  150
  (False, True)   17
  (True,  False)   8     <-- pass at L1, fail at L2
  (False, False)   6
```

**8 of 181 tasks (4.4%) pass at L1 and fail at L2**, where L2 is L1 plus extra text. Under
Blackwell this cannot happen for a Bayes-optimal agent; for a real one with a turn budget it
can, and it is a *result* — but it must be reported, and `LADDER.md` currently reports the
opposite direction (L3 below L2) as the only monotonicity story.

## Part A — is the ladder well defined?

### A1. How the L2/L3 hints are extracted

Both are **static, deterministic, no LLM anywhere** — which is the right call and makes the
rungs reproducible. `code_facts()` (`ladder.py:233`) parses the reference with `ast` and
collects: file-like string literals plus the first arg of any `read_*`/`connect` call; column
names from `df["col"]` subscripts and `.loc[.at[` masks, but only where the receiver was
bound to a `read_*` call; filters from `Compare` nodes inside those masks. `method_hint()`
(`ladder.py:311`) is a **regex**, not an AST: it counts `\.(groupby|pivot_table|…)\s*\(` and
reports the top 6, sorted.

### A2. Are the hints what they claim to be?

Measured over every task that has a reference — 181 test, 275 synthetic, 8 jupyter-agent:

| | test (181) | synthetic (275) |
|---|---|---|
| L2 `Columns used` empty | **118 (65%)** | 4 (1%) |
| L2 `Filters applied` empty | **177 (98%)** | **275 (100%)** |
| L2 adds nothing (cols+filters empty) | **118 (65%)** | 4 (1%) |
| L3 `Method:` empty | 57 (31%) | 0 (0%) |
| L2 columns all already literally in the question | 21 (12%) | **271 (99%)** |
| L3 method all already in the question | 7 (4%) | 149 (54%) |
| `Files read` identical to L1's file list | 37 (20%) | 0 |

Three of these are disqualifying on their own.

**The `Filters applied:` line is dead on every source.** It is empty on 98% of test and 100%
of synthetic. The cause is in `code_facts`: a filter is only recorded when the compared
column sits in a `Subscript` whose receiver is a dataframe-ish name, and models overwhelmingly
write filters as `df[df["Publisher"] == "nintendo"]` where the outer `df[...]` slice is a
`Compare` — which the code does handle — but they just as often write
`df.query(...)`, `.loc` with a boolean mask, or a chained assignment. The rung ships a line
that says `(none)` almost every time. It is noise dressed as a field.

**`Files read` is mostly redundant with L1.** `LADDER.md` is candid that L1 already lists the
files, and `test_the_first_rung_adding_information_is_l2` exists to police it. But the *field
label* is still `Files read: <the same list>`, and on 37/181 test tasks the L2 line literally
restates L1's file list. The rung header says "Notes on the intended computation" and its
first line is information the agent already had.

**L2 is near-vacuous on test by construction.** On 65% of referenced test tasks the entire L2
block is `Files read: … / Columns used: (discover them yourself) / Filters applied: (none)` —
three lines that add nothing beyond L1. `test_no_rung_is_byte_identical_to_the_one_below`
passes because the header line differs, not because any information was added.

**On synthetic, L2 is the reverse problem: it adds nothing because the question already said
it.** 271/275 have every column name appearing verbatim in the question, because the
generator writes "What is the mean of {col} across all rows?" from the column it then selects.
L2's honest summary of such a task is the question restated. 149/275 also have the method
already named in the question.

### A3. The `join` bug in L3 — 34% of test hints are corrupted

`method_hint`'s regex cannot tell a dataframe join from `os.path.join`:

```
test tasks whose L3 method contains 'join': 61
  method hint == literally just "join"     : 56   (31% of all 181)
```

Concrete case, `0000_347_347102_qa_1`:

```
L3 METHOD: join
--- reference ---
BASE_DIR = os.path.join(os.path.dirname(os.path.abspath(__file__)), "input")
CSV_PATH = os.path.join(BASE_DIR, "Pokemon.csv")
...
def pearson(xs, ys): ...
```

The reference computes a hand-rolled Pearson correlation with the `csv` module and never
touches pandas. The rung tells the agent "Method: join", which points it at `pd.merge` on a
single-file table — an actively misleading hint on 31% of test tasks. An AST-based extractor
that filters by receiver type (`join`/`merge` are dataframe ops only when the receiver is not
`os.path` and is not a string literal) reduces these 56 to 0.

There is a second-order effect worth noting: 61 tasks have a hint containing `join`, and the
corrected extractor shows **62% of all test references (113/181) contain no recognised
dataframe method call at all**. The references are largely hand-written `csv`/`sqlite3` code,
so the whole L3 vocabulary misses the idiom the references actually use.

### A4. Five verbatim examples, good and bad

**Good 1 — `syn_Iris_4_mean` (synthetic).** A correct, minimal, non-redundant method line.
```
Q: What is the mean of PetalLengthCm across all rows?
L2: Files read: input/Iris.csv | Columns used: PetalLengthCm | Filters applied: (none)
L3: Method: mean
```
Accurate and specific. The column is already in the question, so the informational content is
thin — but nothing is false.

**Good 2 — `0001_903_1903634_qa_4` (test).** L3 genuinely names the method.
```
Q: What is the p-value from the one-way chi-square test analyzing the distribution
   of gender in math students?
L2: Files read: input/student-mat.csv | Columns used: sex | Filters applied: (none)
L3: Method: sum, value_counts
```
`code_facts` correctly found `sex` via `data["sex"].value_counts()`. `sum` comes from
`counts.sum()` and is a weak but not false signal. This is the shape L2/L3 are supposed to have.

**Bad 1 — `0000_431_431678_qa_5` (test). L3 says "join" for a `csv.Counter`.**
```
Q: How many samples belong to each species in the dataset?
L2: Files read: input/Iris.csv | Columns used: (discover them yourself) | Filters applied: (none)
L3: Method: join
--- reference ---
with open(csv_path, newline="", encoding="utf-8-sig") as f:
    rows = list(csv.DictReader(f))
counts = Counter(r["Species"].strip() for r in rows if r.get("Species"))
print(", ".join(f"{k}={v}" for v in sorted(counts.items())))
```
There is no join, no merge, and no pandas in the reference. The only `join` is
`os.path.join`. The model passed this at L2 and failed at L3 — consistent with the rung having
cost it turns without adding signal.

**Bad 2 — `0000_376_376301_qa_1` (test). L2 is entirely `(none)`.**
```
Q: What is the accuracy of the Gaussian Naive Bayes model in predicting whether an
   insurance company is in the upper quartile of "Insurance Covered Ratio" across
   different DRG categories?
L2: Files read: input/inpatientCharges.csv | Columns used: (discover them yourself) | Filters applied: (none)
L3: Method: (EMPTY)
```
65%-of-test is exactly this. The reference is a 40-line sklearn pipeline using
`Average Medicare Payments`, `Average Total Payments`, `Total Discharges` and
`DRG Definition`; none of them is named, and L3 is blank.

**Bad 3 — `syn_ca_law_enforcement_by_agency_0_mean` (synthetic). The reference is invalid Python.**
```
Q: What is the mean of Total law enforcement employees across all rows?
L3: Method: mean
--- reference (as shipped) ---
import pandas as pd
df = pd.read_csv('input/ca_law_enforcement_by_agency.csv')
result = df['Total law
enforcement
employees'].mean()
```
The column name contains literal newlines. `synthetic_reference` interpolates it into a single-
quoted string without escaping, producing an unterminated literal. `strip_output` and
`redact_literals` both `return source` unchanged on `SyntaxError`, so **L4 ships this broken
program verbatim, prints and all**. 4/275 synthetic tasks are affected. `leak_free()` catches
the answer leak by execution, so no answer is exposed — but the rung hands the agent code that
does not parse, which is a hard failure by construction rather than a measurement.

### A5. Length added per rung, and what L3 adds beyond L2

Characters in the prompt (`n` = tasks with a reference):

| | test median | test p90 | test max | synthetic median |
|---|---|---|---|---|
| L1 | 688 | — | 1163 | 640 |
| L2 | **818** (+130) | — | 1325 | 761 (+121) |
| L3 | **834** (+16 over L2) | — | 1353 | 778 (+17) |
| L4 | 1408 (+574 over L3) | — | 3196 | 1014 (+236) |

**L3 adds 16 characters on median, roughly one line of text, on top of L2.** That is 2% of
the L1 prompt. It is not a rung in any meaningful sense: it is a single comma-separated list
of pandas method names, and on 65% of test tasks L2 itself was already empty, so L3 is
carrying the entire information payload of "L2 and L3" on its own — while being the noisiest
possible extraction of it (`join` bug, 31% empty on test). L4 is the only rung with real
content, and it carries 80% of the added bytes.

Against the run data, L3 is also the rung that looks like it *hurts*: 8/14 = 57.1% at L3
versus 167/181 = 92.3% at L2, with denominators too small to conclude much, but the direction
matches a hint that costs turns and buys one line of unreliable text.

### A6. Is the schema control really answer-free and reference-free?

**Reference-free: yes.** `schema_dump()` touches only `row["files"]` and the tables on disk.
No reference solution, no gold answer. That part of the design is sound and verifiable.

**Answer-free: no.** Running the ladder's own `leaks()` over the generated dumps:

```
schema dumps containing the gold answer (ladder.leaks): 30/250 = 12.0%
```

The `<label>` redaction only fires when a **column name** equals the answer (4/60 dumps in a
spot check). It does nothing about a column **value** appearing in the three sample rows.
Concrete case `0000_324_324293_qa_2`:

```
Q: What is the most common gender among new coders…?
GOLD: 'Male'
dump line: … Employed for wages  NaN  male  0.0  1.0  1.0  1.0 …
```

The answer is sitting in the prompt as a lowercase cell value. `0000_684_684849_qa_2` is the
same story — gold `Acute Care Hospitals` appears verbatim in three sample rows. For a
"most common X" or "which category" task, the dump's three sample rows are close to naming the
answer. This is exactly the informational content `LADDER.md` says the control cannot carry,
and 12% of tasks carry it anyway.

**Size: mostly small, with a real blow-up tail.**

```
dump chars: median=1050  mean=3729  p90=4454  max=154201  (~38,550 tokens)
dumps > 4k chars: 27/250    > 8k: 15    > 16k: 9
```

The worst cases are real and one is absurd: `0000_667_667579_qa_1` and `_qa_3` produce a
**154,201-character dump** (~38.5k tokens) from two wide tables — larger than the model's
entire working context budget is likely to tolerate comfortably. `0115_735_115735943_qa_1`
produces 88.5k chars. `schema_dump` reads `nrows=200` and prints 3 rows of every column, so a
200-column table yields ~600 cells of dense text. There is no width cap, no row cap beyond
200, and no truncation.

Whether it *broke* anything is mixed. Of the 15 tasks with dumps over 8k chars, 11 passed L1
outright (the control never ran), and the failures that did run the control mostly failed at
both rungs. So the blow-up is a budget risk and a confound in the control's favour on exactly
those tasks, not a demonstrated cause of failure. The control's median prompt (1,050 chars)
is smaller than L2's block, so for most tasks the control is a genuinely cheap intervention.

### A7. Is "first passing rung" identifiable at k=1?

**No, and the repo already contains the evidence to prove it.** Four independent L1 runs on
the same 244 test tasks:

```
1111  n=158 (64.8%)   always pass
0000  n= 40 (16.4%)   always fail
0001  n= 21 ( 8.6%)   passed on exactly one run
1110  n= 18 ( 7.4%)   failed on exactly one run
0111  n=  5 ( 2.0%)
0011  n=  2 ( 0.8%)
=> 46/244 = 18.9% of tasks are inconsistent across 4 runs
```

Per-run pass rates on the identical task set: **71.5%, 72.8%, 74.5%, 74.8%** — a 3.3-point
spread from sampling noise alone. The between-task sd of the per-task pass probability is
**0.394**, so the task-to-task variation and the rerun variation are comparable in size.

Two failure modes follow, and both are live in the current numbers:

1. **Bucket churn.** The 21 `0001` tasks sit right at the boundary. At k=1 each is recorded as
   an L1 pass or an L1 failure essentially at coin-flip odds, moving 8.4% of the split between
   the "L1" row and the "needs more information" rows.
2. **Climb-stop bias.** `task_trials` breaks on the first `reward >= 1.0`, so a task that
   would pass at L3 half the time is never measured at L3 half the time. Combined with (1),
   the "lowest passing rung" histogram is a noisy, biased estimator of the quantity it claims
   to report.

On jupyter-agent the same measurement over 161 tasks seen in all four runs gives **6.8%**
inconsistent (11 tasks), and three of the four runs agree with each other exactly — that
source is calmer, but it is also a lower pass rate (41.9%), so it has a different problem
(see Part B).

**Recommendation on k.** Run **every rung on every task** and do not climb. Three reasons,
in order of weight:

- It costs the same number of trials as climbing *when the pass rate is low* and far less
  than k>1 climbing when the pass rate is high. L2 is currently being run on all 181 tasks
  anyway (`climb_test.log`), so the infrastructure already does this.
- It converts every rung into an unconditional pass rate with denominator 250, which is the
  quantity `LADDER.md` says is the headline ("The headline numbers are aggregate pass-rate
  curves by rung"). Climbing cannot produce that; it produces a partition with a
  composition-dependent denominator, which is what produced the 266-for-250 bug.
- It makes the monotonicity test well-defined, because `P(pass at k, fail at k+1)` becomes
  measurable on every adjacent pair instead of only on tasks that happened to climb.

If the full grid is unaffordable, the compromise is **k=2 on every rung**, no climb: the
pass-rate SE on 250 tasks falls from 2.76 to 1.95 points, and P(misclassify a task with true
p=0.25) falls from 0.25 to 0.44 — which is worse, not better, for the *bucket* metric. That
is the argument for reporting **mean pass probability per rung** rather than a first-pass
bucket: `P(pass) = 1-(1-p)^k` is monotone in `p`, so the curve is well defined for any k, and
you can report it with k=1 at a known 2.76-point SE.

Whatever you do, report the rerun variance next to the headline. "74.8%" and "71.5%" are the
same experiment.

### A8. Remaining leak paths

Ranked by how much they cost.

1. **The schema control leaks the answer on 12% of test tasks** (A6). Highest impact: it
   corrupts the one condition whose entire purpose is to be answer-free.
2. **The `os.path.join` bug makes L3 actively misleading on 31% of test tasks** (A3). Not an
   answer leak, but it is information that is false, which the Blackwell argument does not
   permit and which the leak oracle cannot catch — `leak_free()` tests for the answer, not for
   truthfulness.
3. **The `Filters applied:` / `(discover them yourself)` placeholder text** (A2) is not a
   leak, but it is a rung that adds a constant string, so it is byte-different from L1 and
   passes `test_no_rung_is_byte_identical_to_the_one_below` while carrying zero information.
   That test checks the wrong property.
4. **The `synthetic_reference` newline bug** (A4, bad 3) ships unparseable code at L4 with
   prints intact. `leak_free()` catches the answer, so the exposure is nil, but the guard
   only works because `leak_free` exists; `strip_output` alone does not protect anything.
5. **`redact_literals` on a `SyntaxError` reference is a no-op** (same code path as 4). On
   model-written references this would strip nothing; today 0/181 test references fail to
   parse, so the exposure is currently zero, but it is a fail-open default in a security-
   relevant function. `strip_output` and `redact_literals` should fail *closed*, or at
   minimum `leak_free` should be the only thing permitted to hand an unparsed payload to L4.
6. **Residual text leaks.** `logs/ladder_test.log` reports 24 tasks with a residual leak
   (13 `task_inherent`). Those are L1 hits on the unmodified question, which is the
   differential guard working as designed.

One genuine strength: the design's insistence that hints come from a *verified* reference, that
the L4 payload is re-run and graded, and that a still-passing L4 is excluded rather than
repaired, is the right set of checks and it is implemented. The gap is that the checks cover
*the answer leaking into a hint*, and miss *a hint being wrong*, *a rung being empty*, and
*the control leaking the answer* — which is where the actual damage is.

## Part B — colour on the tasks

### B1. Distributions

Heuristics are stated so they can be argued with. **Operation family**: ordered regex list,
first match wins — `count` (`how many|number of|count`), `filter` (`only|where|for each|with|
that (is|are)|considering|excluding|among`), `groupby` (`per|by <category-word>|breakdown`),
`agg` (mean/median/sum/total/largest/highest/top/most/correlation/…), `argmax_typ`
(`which|most common|most frequent`), `stat_test` (`p-value|chi-square|t-test|anova|pearson|
regression|fit|predict|classifier|model|auc|accuracy|coefficient|feature`), `join`, `lookup`,
`rank`, `diff`, `string` (`percentage|fraction|proportion|share`). **MC**: three or more
`(A)`-style or `1.`-style inline options, or the phrase "which of the following".

**SmolDataEnvs `test` (250)**

| feature | value |
|---|---|
| reward_mode | numeric 132, exact_short 87, exact_bool 29, flexible 1, list_csv 1 |
| difficulty_tier | easy 33, medium 118, hard 99 |
| answer type | numeric 136, label 83, bool 29, list 2 |
| **multiple-choice** | **1/250 = 0.4%** |
| n_files | 1:166, 2:42, 3:15, 5:6, 9:7, 19:4 |
| input size | median 0.52 MB, p90 123 MB, max 601 MB |
| question length | median 17 words, max 30 |
| operation family | agg 97, count 60, filter 36, **stat_test 32**, other 7, groupby 7, argmax 6, string 4, lookup 1 |

**SmolDataEnvs `eval` (144)** — same shape: numeric 83 / exact_short 56 / exact_bool 5; easy 16
/ medium 74 / hard 54; median 16 words; median 0.98 MB, max 4.78 GB.

**synthetic (275)** — numeric 149 / exact_short 126; no difficulty tier (all `0`); median **10
words**, max 13; **every task is `agg`**; n_files 1:112, 2:68, 8:29, 19:20; median 3.45 MB.

**jupyter-agent (2,000 extracted)** — numeric 1,520 / exact_short 424 / exact_bool 56; no tier;
median 15 words; n_files 1:1,663, 2:240, 3:51; median 0.85 MB, max 897 MB; agg 698, count 664,
stat_test 226, filter 175, string 77, other 68, lookup 42, groupby 26, argmax 19.

Three things stand out.

**The multiple-choice claim in `LADDER.md` is wrong by two orders of magnitude.** It says
"52/250 test tasks are multiple choice, where the answer is one of the options in the
question". Across nine independent heuristics on all 250 rows — lettered options, numbered
options, "which of the following", "options", "candidates", question-final `(A)`, and the `or`
-alternative shape — the best detector finds **1 task (0.4%)**. The longest question in the
whole split is 211 characters. Only **13/250 (5.2%)** have the gold answer as a substring of
the question, and those are incidental (`no` inside a longer word, etc.), not options. The
`ladder.py:484` comment repeating "52/250 tasks are multiple choice" is the same error
propagated into code. This matters because `task_inherent` (13 per `ladder_test.log`) is
reported as a property of MC tasks; it is really a property of something else.

**The benchmarks measure different things and should never be pooled.** Synthetic is 100% single
family (`agg`) with 10-word questions; SmolDataEnvs `test` is 39% `agg` + 24% `count` + 13%
`stat_test` with 17-word questions; jupyter-agent is 35% `agg` + 33% `count` + 11% `stat_test`.
A ladder result on synthetic and a ladder result on jupyter-agent are not comparable, and
neither is comparable to `test`.

**`stat_test` is a large, distinct, and hard slice.** 32/250 on test (12.8%), 226/2,000
(11.3%) on jupyter-agent — and these are the tasks where the "answer" is an artifact of a
method choice, which is exactly where Part B's failure analysis finds the trouble.

### B2. L1 pass rate by feature

From `data/runs/<split>/*/L1/result.json`. n_runnable: test 250, synthetic 275,

### B3. Hand-read failure analysis (all 63 L1 failures on test)

Every failure was read: `question`, `gold`, `prediction`, `solution.py`, `result.json`,
`turns.json`.

| category | n | % |
|---|---|---|
| **grader strictness** (right answer, wrong surface form) | **21** | **33.9%** |
| genuine model error | 11 | 17.7% |
| timeout / harness (no solution, or 40 turns spent) | 11 | 17.7% |
| arbitrary task (answer depends on an unstated free parameter) | 7 | 11.3% |
| ML nondeterminism (seed/split/scaler decides the number) | 5 | 8.1% |
| ambiguous question | 4 | 6.5% |
| scale/format mismatch (fraction vs percent) | 1 | 1.6% |
| wrong gold (count disagrees with the table) | 2 | 3.2% |

**Only 34% of failures are failures of reasoning.** Representative cases:

*Grader strictness.* `0000_428_428622_qa_2`: gold `North America`, pred `NA` — the agent picked
the right region. `0000_764_764519_qa_3`: gold `Male`, pred `M`. `0000_868_868084_qa_4`: gold
`São Paulo`, pred `SP`. `0001_046_1046894_qa_3`: gold `PCA-reduced features`, pred
`PCA-reduced`. `0000_458_458419_qa_1`: gold `Sea Surface Temperature`, pred `Sea Surface Temp`.

I re-graded these under trivial reformulations (strip an `ANSWER:` prefix, take the first
token, expand hyphens). **7/21 flip to 1.0**, and 5 of those 7 flip by removing nothing but
the literal string `ANSWER: `:

```
gold='yes'                       pred='ANSWER: yes'                 -> 0.0
gold='Sales Representative'      pred='ANSWER: Sales Representative'-> 0.0
gold='Size(sqf)'                 pred='ANSWER: Size(sqf)'           -> 0.0
```

Scaled across the split: **`ANSWER: <gold>` fails to grade while `<gold>` passes on 110 of the
116 exact-mode test tasks.** The prompt explicitly asks for "just the value", and the agent
complied in substance and lost the point in a prefix. The other 14 of the 21 are genuine
label-vocabulary mismatches (`NA` vs `North America`, `SP` vs `São Paulo`, `50,50,50` vs a
gold of `50` for a three-group question where the gold is itself a single number).

*Arbitrary task.* `0000_455_455476_qa_5`: "the total stat threshold that separates
'legendary or pseudo-legendary' Pokémon" — this is Pokémon domain lore, not in the data; the
agent chose 600 (the community-standard pseudo-legendary cutoff), the gold says 575.
`0001_381_1381379_qa_2`: "features remaining after removing redundant features based on
correlation analysis" — the reference chose `|r| >= 0.99`; the agent chose the same idea, got
18 instead of 17. `0000_419_419818_qa_1`: "the year mixtapes became competitive with albums"
— the reference invented `MIN_RELEASES = 5`. No analyst could recover these from the question.

*Timeout/harness.* 11/63. Five hit the 1200 s wall with no `solution.py` at all
(`0065_262_65262139_qa_5`, `0075_374_75374659_qa_2`, `0115_735_115735943_qa_1`,
`0138_500_138500445_qa_1`, `0064_089_64089732_qa_5`). Six exhausted 40 turns or wrote a
program that never produced output (`0014_516_14516985_qa_4` vendored lightgbm/optuna that
aren't installed offline; `0126_223_126223416_qa_5` ran an XGBoost grid to turn 30 with no
prediction). `0000_419_419825_qa_2` wrote nothing in 11 turns. These are budget failures
masquerading as capability failures, and the ladder counts them as information failures.

*ML nondeterminism.* `0001_043_1043420_qa_4` ("how many benign cases were misclassified as
malignant" — gold 3, pred 2, differs by `random_state`), `0000_566_566544_qa_3` (precision
0.694 vs 0.753, split-dependent), `0036_284_36284344_qa_5` (max F1 over a model panel,
fold-dependent). The gold answer is one draw from a distribution the question does not pin.

*Grader tolerance.* 76% of failures (48/63) are on tasks graded with `atol = rtol = 0`. Of the
numeric failures, 14 land within 10% of gold — i.e. close, and called wrong.

**The synthetic L4 = 0/64 result is now explicable, and it is the ladder's own design.** L4
hands the agent the spec rendered as code, prints stripped. The agent then has to reproduce
the *computation*, and 64/64 failures are the model rewriting it and getting a different
answer. The verifier-fix commit notes the synthetic L4 payload reproduces gold in 23/30 cases,
so the rung is sound and the model is the limit. But L3 (1/65) sitting below L2 (13/78) with
both below L1 (179/275) is a clean monotonicity violation ladder: L1 > L2 > L3 > L4 on
synthetic, monotonically *decreasing* with more information. That is worth reporting as-is;
`LADDER.md` mentions only L3 below L2.

## Part C — is it "too easy"?

### C1. The evidence

**The 74.8% L1 number is real, and it is not the problem.** 74.8% is the pass rate of a strong
agent on SmolDataEnvs `test`, with a 3.3-point rerun spread (71.5–74.8% across four runs). It
is not saturated, and 25% headroom is enough to measure a training effect.

**The benchmark is too easy for the *ladder*, and for a reason that is structural.** The
ladder's failure mode is "the question underdetermines the intended computation". On this
benchmark that almost never happens, because the questions are short and heavily templated:

- median question length is **17 words**, max 30, over all 250;
- **39% are a single aggregate** (`agg`) and **24% are a count**;
- **0.4% are multiple choice**, and the whole `eval` split has 144 similar rows;
- the operation families that *do* stress a model — `stat_test`, joins, multi-file, ML fits —
  are 13%, ~0%, and ~4% respectively.

So there is very little for L2/L3 to disambiguate: the question already names the column, the
filter is usually stated or absent, and the method is a single `agg`. That is exactly what the
hint audit measures independently (A2: L2 empty on 65% of test; 99% of synthetic L2 columns
already in the question). **Two independent lines of evidence agree that the ladder has almost
nothing to measure here, and the existing results are consistent: of 23 L1 failures with a
reference, the control rescued 11 and a hint rescued 12.**

**The bigger headroom problem is not pass rate, it is the 66% of failures that are not
reasoning failures.** If two thirds of the residual 25% is grader surface form, timeouts, and
seed noise, then the *reasoning* signal on this benchmark is roughly 8 points wide
(11 genuine errors out of 250 = 4.4% absolute). A training effect smaller than ~4 points is
invisible. That, not the 74.8%, is what makes this benchmark a poor instrument right now.

**jupyter-agent is the better instrument and is under-used.** At 41.9% L1 it has twice the
headroom, and its difficulty is concentrated in exactly the families where information helps:
`stat_test` 21.6%, `lookup` 21.4%, `groupby` 27.3%. It is also the only source with no
reference solutions at all (8/2000, because `gen_refs.py` has not been run at scale), so
**the ladder currently cannot be run on the source that needs it most.** That is the single
highest-value piece of missing work, and it is cheap: the reference generator already exists
and already verifies offline.

### C2. Options, ranked by expected information per dollar

Ranked on (signal gained) / (cost), assuming the current headline needs to support a claim
about training.

**1. Generate jupyter-agent reference solutions and run the ladder there. (Highest value.)**
Cost: `gen_refs.py` on ~1,000 e2b tasks, then a 4-rung sweep. Why it wins: the source already
has 41.9% L1 (2× headroom), 0% reference yield is the only reason it is unusable, and its
`stat_test` slice (21.6%) is where information should matter. Deciding data: if the L1→L2 gap
on jupyter-agent is larger than ~10 points, the ladder has a home; if it is ~2 points, the
method is dead everywhere and should be reported as such.

**2. Fix the defects that currently corrupt rungs, before any new run. (Cheapest.)**
(a) `method_hint`: AST-based, receiver-filtered — kills the `join` bug on 31% of test tasks.
(b) `schema_dump`: drop sample *values* for any column whose value matches the gold, and cap
at ~20 columns / ~4k chars — closes the 12% answer leak and the 38.5k-token blow-up.
(c) `strip_output`/`redact_literals`: fail closed on `SyntaxError`; fix the newline
interpolation in `synthetic_reference` — the 4 broken L4 payloads.
Deciding data: none needed. These are unambiguous; the current numbers cannot be reproduced
with them unfixed. (The fourth item from the first draft of this section — the
`summarize.py` double-count — was fixed concurrently in `31d3e74` and is no longer outstanding.)

**3. Report pass-rate curves with no climb and k=2, plus rerun variance. (Moderate cost.)**
Cost: 4 rungs × 250 tasks × 2 samples = 2,000 trials for test. Buys a SE of 1.95 points
instead of 2.76, a well-defined monotonicity test, and the 4.4% L1-pass/L2-fail violation
becomes a headline instead of a hidden finding. Deciding data: already in hand — the four
existing L1 runs. This is a reporting change, not an experiment.

**4. Fix the grader surface before measuring anything on exact-mode answers. (Cheap, high
leverage.)** Report a second metric alongside pass@1: "substantive pass" = does any trivial
reformatting of the last line grade 1.0. On the 63 current failures that recovers 7 tasks
(3 points of absolute pass rate) *without changing any model behaviour*. Also: drop the 11
timeout/harness failures from the denominator or report them as a separate row — they are
currently counted as information failures. Deciding data: in hand (B3).

**5. Harder filters for jupyter-agent (rank by hardness, keep the ladder).** The 2,000-row
extract is dominated by `count` and `agg`. Applying the B2 slices — `stat_test`/`lookup`/
`groupby` only, plus `input > 10 MB`, plus `edu_score` if it correlates — yields a pool where
L1 is ~25–30%, which is where a ladder is informative. Cost: zero (it is a filter). Deciding
data: the pass-rate-by-feature table in B2 already predicts it; the filter's yield is the
only unknown.

**6. Rungs below the current L1. (Interesting, and the cheapest way to test the thesis.)**
The owner's suggestion — hide file names, drop the question's naming of the column — gives
*rungs the agent can pass that are strictly weaker than L1*. This directly tests whether the
ladder measures something ordered, and it costs nothing extra to build. Two concrete rungs:
- **L0-files**: L1 with `Files:` replaced by "the input directory contains one or more tables"
  (naming files is a real hint: it was removed from L1 for exactly this reason, per A2's
  `Files read` redundancy finding).
- **L0-col**: L1 with the column name replaced by a placeholder ("the column under study").
Deciding data: if a model passes L0-files and fails L1 on >10% of tasks, the information
gradient is real and measurable *below* the current floor, which would also explain why the
ladder has little to measure above it. If ~0%, the model's ceiling is skill and the ladder
should be retired rather than extended.

**7. Evaluate a weak model instead of a strong one. (Most expensive, and probably wrong.)**
A 2B model would put L1 near 30% and give the ladder room. But RQ4 is *"does training lower
the rung needed"*, which is an **arm-vs-arm comparison at fixed model**, not a model-vs-model
one. A weak model makes every arm look bad and the ladder noisy. The right move is to keep
the strong model as the instrument's calibrator (it is what tells you the ceiling) and add
one weak arm only once options 1–3 are in place, so that any rung effect is attributable.

### C3. What would decide between the options

| question | the data that decides it | already have it? |
|---|---|---|
| Does the ladder measure anything on a harder source? | L1→L2 gap on jupyter-agent `stat_test`+`lookup`+`groupby` (n≈111), k=2 | **no** — needs references (option 1) |
| Is the current ladder broken or just idle? | Recompute L2/L3 emptiness + the `join` bug count after fixes 2(a,c) | **yes**, computed above |
| How much of the 25% residual is real signal? | Substantive-pass rate + timeout exclusion on the 63 read failures | **yes**, B3 |
| Is the information gradient real below L1? | L0-files / L0-col pass rates vs L1 on the same 250 | **no** — one cheap sweep |
| Is the ladder measuring training? | L1–L4 curves for arm 0 vs R-SFT vs R-GRPO, same tasks, k=2, no climb | **no** — the actual experiment |

The short version: the ladder is not ill-defined in its *ordering* (the Blackwell containment
property is tested and holds), but two of its four rungs are empty or noisy on the primary
source, the control leaks on 12% of tasks, and the published headline came from a superseded
run. The benchmark is not too easy in the pass-rate sense; it is too easy in the sense that
66% of its failures are not reasoning failures, which leaves ~4 points of measurable signal.
