# Audit: LADDER.md headline numbers vs. raw per-trial results

Read-only audit, 2026-10-01. No sweep was run, no OpenRouter credit was spent, and no file in the
repo was modified. Everything below is recomputed from `data/runs/<split>/<task>/<rung>/result.json`
and cross-checked against `logs/*.log` and `git log -p`.

**Bottom line: the `test` table in LADDER.md is withdrawn in full. It describes a run that no
longer exists on disk, and its central claim (92% of L1 failures rescued by the schema control)
is not supported by any surviving data — the surviving control shows 36.5%.**

### `synthetic` — 275 tasks, 757 trials on disk

| rung | attempted | pass | pass rate |
|---|---|---|---|
| L1 | 275 | 179 | 65.1% |
| L1+schema | 275 | 197 | 71.6% |

First-passing rung: L1 179, L2 8, L3 1, never 87 (total 275). Every task has a by-construction

**The 87 "never" is a broken-gold problem, not a model or harness problem.** The split of the 87:
64 reached L4 and 23 stopped at the control. For all 64 L4 trials, I re-executed the task's own
recorded `ops` against the full CSV that the agent actually saw. In **64 of 64** cases the full-table
computation does **not** reproduce the gold answer, while the model's prediction does. Concretely:

| task | gold | model's answer | sum over full table |
|---|---|---|---|
| `syn_runs_2_sum` (`sum(horse_no)`) | 345296 | 548631 | 548631 |
| `syn_GlobalLandTemperaturesByMajorCity_2_sum` | 47223.8 | 221179.939 | 221179.939 |
| `syn_GlobalLandTemperaturesByMajorCity_4_mean` | 19.5145 | 18.12597 | 18.12597 |

Root cause: `synthetic.py:iter_tables()` reads with `pd.read_csv(path, sep=sep, nrows=50_000)`
but writes the *untruncated* file into `data/inputs`. The answer is computed over the first 50,000
rows; the agent reads all of them. `runs.csv` has 79,447 rows and
`GlobalLandTemperaturesByMajorCity.csv` has 239,177. Any task whose table exceeds 50k rows is
mis-graded by construction — 58 of 275 tables exceed it, and 38 of the 64 L4 tasks are in that set.

This also disposes of a live disagreement in the git history. Commit `09365ea` ("Fix a verifier
mount that silently graded trials 0.0") concluded that synthetic L4 at 0/64 was "a real model
result, not a broken spec". That conclusion is wrong on the evidence above: the gold answer is the
broken part. Its supporting check — "the L4 payload reproduces the gold answer when run offline in
23/30 cases" — is consistent with my finding, since the payload was run against the same truncated
frame that produced the gold, and cannot see the truncation.

The `synthetic` L1/L1+schema pair is still usable: L1 and the control are unaffected by this bug
because the question asks for a whole-table aggregate and the model computes over the whole table.
Their *relative* comparison is contaminated, since a task whose gold is truncated is unpassable
under either prompt. Treat the synthetic pass rates as upper bounds on nothing and lower bounds
on nothing in particular; the honest statement is that the split is not yet gradeable.

### 2.3 Were results overwritten?

Yes, by design. `run_ladder.py:once()` reuses `result.json` when the prior run exited cleanly
(`prior.get("agent_status") == "exit 0" or not retry_failed`), so each rerun silently *replaces*
the stored result for crashed trials and inherits cached results for clean ones. The mtimes show
the current tree was written by exactly two runs on Sep 29:

```
L1        250   00:31:33 -> 01:32:08     (rerun_test.log)
L1_schema  63   00:32:00 -> 01:45:33     (rerun_test.log)
L2        181   01:49:13 -> 02:08:17     (climb_test.log)
L3         14   01:49:43 -> 02:16:03     (climb_test.log)
L4          6   01:49:57 -> 01:55:45     (climb_test.log)
```

Every one of those 514 files is newer than every number in the doc. `climb_test.log` is a bare
`--rungs L2,L3,L4` re-climb: it emits 250 L2 lines, of which 69 are the runner's
`"no verified reference"` skip (printed with no `agent_status`, `reward=0.0`), leaving 181 real
trials — matching the 181 L2 directories on disk. Its 83 L3 lines and 75 L4 lines likewise
contain 69 skips each, leaving 14 and 6, exactly matching disk. The on-disk tree and the two logs
reconcile perfectly, so the current tree is internally consistent and is a faithful record of
those two runs.

| commit | time (local) | change |

Consequences, which matter:

- **`6b4b414` changed the L1 prompt itself** (`- files = ... row["files"]` → `input_files(row, split)`),

- **`62f40a6` changed what L2–L4 do on the 69 reference-less tasks**: before, `prompt_for` fell
  back to the L1 text and the runner spent a trial re-measuring L1; after, those rungs are skipped.
  The doc's "L2 9/14" predates that change.
- **`62f40a6` also changed synthetic references**, adding `synthetic_reference`, so synthetic
  L2–L4 prompts differ entirely from the doc's era.

**Do results on disk mix ladder versions?** For `test`, no. All 514 files are from after the final
rung change, and the prompts are rebuilt from `ladder.py` at run time rather than cached. One
inconsistency survives: `climb_test.log` wrote its L2/L3/L4 at 01:49–02:16 while `62f40a6`
committed at 00:37, so all rungs are post-`62f40a6`. Good. The mixing is between *the doc and
the disk*, not within the disk.

### 2.5 The verifier bug: does it invalidate the `test` numbers?

Commit `09365ea` (Sep 29 02:28) fixed an offline-verifier mount that could grade trials 0.0
silently. It claims the blast radius was measured and the collected numbers stand. I tested the
claim rather than accepting it.

I reproduced the pre-fix bwrap invocation. It fails only when the bind *source* resolves outside
the work directory:

```
bwrap: Can't bind mount /oldroot/tmp/audit/v3/inputs on /newroot/tmp/work/input:
       Unable to mount source on destination: No such file or directory
```

The `test` inputs resolve to `/home/evan/Documents/smol-ladder/data/inputs/...`, so the old
invocation **would** have failed for this split. Two artifacts settle whether it actually did:

1. `verify/input` is a **real directory** in 242/242 checked `test` L1 trials and 275/275 synthetic
   trials, and a **symlink** in 678/692 jupyter-agent trials. Only the new `shutil.copytree` path
   produces a directory. So the `test` and `synthetic` trees on disk were produced by the *fixed*
   verifier.
2. All 514 `test` files have mtimes at 00:31–02:16, and the fix committed at 02:28 — after. The
   copies were made by code already carrying the fix (the fix was in the working tree during the
   runs; only the commit is later).

Independent confirmation that the verifier ran: 187 L1 trials scored `reward 1.0` with non-empty
predictions. A silently-failed mount yields empty stdout and `reward 0.0`, so a non-zero pass count
is impossible without a working verifier.

**Verdict: the `test` and `synthetic` numbers on disk are sound.** The 7 `test` trials with a
`solution.py` but an empty prediction are the residue of that bug window and should be rerun; the
other 14 empty predictions have no `solution.py` and are genuine agent failures.

**The `jupyter-agent` split did use the old verifier** (symlinked `verify/input`, and its trials
ran 10:27–11:09 on Sep 29 — after the 02:28 commit, so the *committed* fix was in place, yet the
symlink shape says the old code path ran). This is unexplained and I am marking it **unknown**;
it is a third reason not to use that split's numbers.

## 3. The bug that makes `summary_test.json` sum to 266

`smol_ladder/summarize.py`, in the `hist` loop:

```python
climbed += 1
# The control is not a rung: ... never counts as the "information" rescues below.
if rungs.get("L1+schema", {}).get("reward", 0.0) >= 1.0:
    hist["L1+schema"] += 1
first = next((r for r in ["L2", "L3", "L4"]
              if rungs.get(r, {}).get("reward", 0.0) >= 1.0), None)
hist[first or "never"] += 1
```

Every climbed task increments **two** buckets: once for the control, and once again for
`first or "never"`. There is no `continue` after the control branch, so a task rescued by the
control is counted as both "L1+schema" and "never". The comment states the intent correctly — the
control rescue must not be double-counted — and the code does the opposite.

Replicated exactly: `L1 187, L1+schema 16, L2 17, L3 3, L4 3, never 0, no reference 40` = **266**
for 250 tasks, byte-identical to the committed `summary_test.json`. The same double-count inflates
`summary_synthetic.json` to 298 for 275 tasks. The bug has been present since the code was first
committed in `d4a1db2` (Sep 28 20:08).

The true partition, mutually exclusive, over all 250 tasks is:

| rung / status | tasks |
|---|---|
| L1 | 187 |
| L2 | 17 |
| L3 | 3 |
| L4 | 3 |
| never (all 40 reference-less failures) | 40 |
| **total** | **250** |

The climbable set is exactly 23 tasks — the L1 failures that have a verified reference. Every one of
those 23 passed at some rung: 17 at L2, 3 at L3, 3 at L4, and **0 never**. So on this split the
"never" count is 40, and all 40 are the reference-less tasks, which were never tested against
L2–L4 at all. The doc's framing of a ladder that leaves a residue of hard tasks is wrong for this
data: once a task has a reference, it always passed somewhere.

The control rescues 23 L1 failures, and they split 16 with a reference / 7 without. That is the
whole explanation for the summary file's 16: `summarize.py` credits the control only inside the
`have_source` branch, so the 7 reference-less rescues are never recorded at all, while the 16 it does
record are each also booked into a ladder bucket.

So the 266 decomposes exactly:

```
187  L1 passes
 16  control rescues, double-counted (16 of them also appear as L2/L3/L4)
 17  L2   \
  3  L3    > these 23 are the same 23 tasks as the 16 above
  3  L4   /
  0  never (never never fires once the 16 stop masking it)
 40  no reference (all 40 are genuinely 'never', they just never reach that branch)
----
266
250 tasks, inflated by 16 double-counted control rescues
```

Note the second failure mode visible here: `hist["never"]` reads **0** even though 40 tasks on disk
never passed at any rung. The 40 are caught earlier by the `no reference` branch, so the true
"never" bucket stays empty and the summary reports that nothing was ever failed-through, when in
fact the reference-less failures are exactly that. A third, separate problem: a task that has no
L2–L4 trial on disk (skipped by `62f40a6`, or the climb never reached it) is indistinguishable in
this code from one that was tried and failed.

**Also worth fixing before any rerun** (code changes, not trials — listed because each one
invalidates a number in the report above):

- `summarize.py`: add a `continue` after the control branch so a control rescue is counted once.
  Better, emit two explicit mutually-exclusive partitions: `first_passing_rung` over the ladder

## Appendix: the script

Reruns with `python3 audit_numbers.py` from the repo root. Reads only; writes nothing.

```python
"""Recompute every ladder number from raw per-trial results. Read-only."""
import collections, datetime, json, re, sys
from pathlib import Path

DATA = Path("data/runs")
RUNG_DIRS = ["L1", "L1_schema", "L2", "L3", "L4"]   # "L1_schema" is the filesystem spelling
LOG_LINE = re.compile(r"\[(\d+)/(\d+)\]\s+(\S+)\s+(\S+)\s+reward=([\d.]+)\s+pred='(.*)'\s*(.*)$")


def collect(split):
    """task_id -> rung_dir -> parsed result.json."""
    out = collections.defaultdict(dict)
    for p in (DATA / split).glob("*/*/result.json"):
        r = json.loads(p.read_text())
        r["_mtime"] = datetime.datetime.fromtimestamp(p.stat().st_mtime).isoformat(timespec="seconds")
        out[p.parent.parent.name][p.parent.name] = r
    return out


def is_harness_failure(r):
    """A trial the harness lost, not the model: the agent never finished."""
    return r.get("agent_status") != "exit 0"


def rung_census(runs):
    print(f"{'rung':<11}{'attempted':>10}{'pass':>7}{'rate':>8}{'harness-fail':>15}")
    for rd in RUNG_DIRS:
        seen = [d[rd] for d in runs.values() if rd in d]
        if not seen:
            print(f"{rd:<11}{'(not run)':>10}")
            continue
        ok = sum(r["reward"] >= 1.0 for r in seen)
        hf = sum(is_harness_failure(r) for r in seen)
        print(f"{rd:<11}{len(seen):>10}{ok:>7}{ok/len(seen):>8.1%}{hf:>15}")


def first_passing(runs, label):
    """Mutually exclusive partition. The control is deliberately excluded."""
    hist = collections.Counter()
    for d in runs.values():
        if "L1" not in d:
            hist["no L1 result"] += 1
        elif d["L1"]["reward"] >= 1.0:
            hist["L1"] += 1
        else:
            hist[next((r for r in RUNG_DIRS[2:] if d.get(r, {}).get("reward", 0) >= 1.0),
                      "never")] += 1
    print(f"\nfirst passing rung [{label}]: " + ", ".join(f"{k}={v}" for k, v in hist.most_common()))
    print(f"  SUM={sum(hist.values())}  tasks={len(runs)}")


def control(runs):
    """L1+schema, on the L1 failures only, which is how it was designed to run."""
    fails = {t for t, d in runs.items() if d["L1"]["reward"] < 1.0}
    ran = {t for t, d in runs.items() if "L1_schema" in d}
    ok = sum(1 for t in ran if runs[t]["L1_schema"]["reward"] >= 1.0)
    print(f"\ncontrol: ran on {len(ran)} tasks; == the L1-failure set? {ran == fails}; "
          f"run on any L1 passer? {len(ran - fails)}")
    print(f"  rescue {ok}/{len(ran)} = {ok/len(ran):.1%}" if ran else "  not run")


def reproduce_summarize_bug(split, source_for, read_source):
    """Replicates summarize.py's double-count to show why its JSON sums too high."""
    rows, _ = source_for(split)
    by_id = {r["task_id"]: r for r in rows}
    runs = collect(split)
    hist = {k: 0 for k in ["L1", "L1+schema", "L2", "L3", "L4", "never", "no reference"]}
    for task, d in runs.items():
        if "L1" not in d:
            continue
        if d["L1"]["reward"] >= 1.0:
            hist["L1"] += 1
            continue
        if read_source(by_id[task], split) is None:
            hist["no reference"] += 1
            continue
        if d.get("L1+schema", {}).get("reward", 0.0) >= 1.0:
            hist["L1+schema"] += 1          # <-- no continue: double-counts below
        first = next((r for r in ["L2", "L3", "L4"]
                      if d.get(r, {}).get("reward", 0.0) >= 1.0), None)
        hist[first or "never"] += 1
    print(f"\nsummarize.py replication [{split}]: {hist}")
    print(f"  SUM={sum(hist.values())} vs tasks={len(by_id)}  (inflated by the missing continue)")


def log_tally(name):
    """Recover a run's own numbers from its log, to date results on disk."""
    path = Path("logs") / name
    if not path.exists():
        return
    per = collections.defaultdict(lambda: [0, 0, 0])   # lines, pass, skipped-no-reference
```

For the synthetic gold-answer check, which needs the input tables:

```python
import pandas as pd
from smol_ladder.jtasks import synthetic_input_dir, load_synthetic

OPS = {"mean": "mean", "median": "median", "sum": "sum", "max": "max"}

def truth(row, df):
    """Re-execute a synthetic task's recorded ops against the SHIPPED table."""
    v = df
    for op in row["ops"]:
        name, _, arg = op.partition("(")
        arg = arg.rstrip(")")
        if name == "filter":
            col, _, want = arg.partition("==")
            v = v[v[col] == want]
        elif name == "value_counts":
            v = v[arg].value_counts(dropna=True)
        elif name == "argmax":
            v = v.index[0]
        else:
            v = getattr(pd.to_numeric(v[arg], errors="coerce").dropna(), OPS[name])()
    return v

for row in load_synthetic():
    df = pd.read_csv(synthetic_input_dir(row) / row["files"][0])
    if len(df) > 50_000:
        print(row["task_id"], "gold", row["answer"], "actual", truth(row, df))
```
